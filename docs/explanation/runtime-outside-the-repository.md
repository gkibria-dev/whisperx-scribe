# Why the runtime lives outside the repository

## The situation

The Python environment for this project is about 2 GB: PyTorch, CTranslate2, pyannote and their
dependencies. The repository itself is a few hundred kilobytes of PowerShell, Python and
Markdown.

A virtual environment inside the project folder is the usual Python convention, and it is the
wrong choice here. This repository lives in a synced folder, which means a `.venv` beside it
would be uploaded, downloaded, scanned and versioned by the sync client, repeatedly, for files
that are regenerated by one command.

Generated output has the same problem in a smaller way. Transcripts, test artifacts and
throwaway environments do not belong in version control, and `.gitignore` only stops them being
committed, not from being created there and synced.

## The split

```text
REPOSITORY                          RUNTIME
(in Git, synced)                    (%LOCALAPPDATA%, machine-local)

scripts, tests, docs                venv\           the Python environment
settings.json        configures ▶   output\         transcripts, when output.mode = directory
settings.local.json                 test-output\    test artifacts
                                    test-venv\      the clean-install test's environment
```

`%LOCALAPPDATA%` is the Windows location for exactly this: per-user, per-machine data that is
not roamed and not backed up. The repository holds the description of the runtime, and the
runtime holds the bytes.

## No environment discovery, on purpose

`run_pipeline.ps1` resolves one path, `environment.venvPath`, and fails if nothing is there. It
does not look for `.venv`, `env` or `whisperx-env` in the repository, and it does not activate
anything. It invokes the interpreter by absolute path.

A fallback search would be friendlier in the moment and would undo the whole arrangement. If an
in-repository environment works when it exists, then it will exist: someone will create one out
of habit, the 2 GB will be back inside the synced folder, and nothing will report it. A hard
failure with a message that says which path was expected keeps exactly one answer to "which
environment is this using".

`Get-LegacyEnvironmentPaths` exists for the same reason, in the opposite direction. It reports
an old in-repository environment during setup so that it can be deleted, but nothing may use
its result to decide what to run.

## Tests must not touch the real environment

The two slow tests would each be capable of destroying the environment you work with, so both
are pointed elsewhere by construction:

- `test-clean-install.ps1` builds its own environment under `test.environmentPath`, passes that
  path explicitly to the copied `setup.ps1`, and excludes `settings.local.json` from the copy so
  a local override cannot redirect it back. It aborts if the test path and the real path overlap.
- `test-pipeline.ps1` writes to a per-run folder under `test.outputDirectory` and deletes it on
  success, keeping it when the run fails, because a failed run's artifacts are the evidence.

The rule those two follow is that `git status` is clean after any test.

## What this costs

Cloning the repository does not give you a working setup. That is the trade: one setup command
per machine, in exchange for a repository that stays small, syncs quickly, and never carries
anyone's binaries. Moving the environment is a settings change and a rebuild, not a copy.
